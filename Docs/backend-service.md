# Бэкенд-сервис

Шаблон, по которому устроен каждый бэкенд-сервис. Образец реализации — `Backend/PingService`.

## Состав решения

Сервис — это решение из четырёх проектов. Каждый проект представляет один слой.

| Слой | Ответственность |
| --- | --- |
| `*.Domain` | Модель предметной области: сущности и бизнес-правила |
| `*.Application` | Прикладная логика: команды и запросы |
| `*.Infrastructure` | Работа с внешними системами: хранилища, сторонние API |
| `*.Api` | Точка входа: HTTP-контроллеры и сборка приложения |

## Зависимости между слоями

```
            Api
        ↙        ↘
Application    Infrastructure
        ↘        ↙
           Domain
```

Стрелка читается как «зависит от». Правила:

- `Domain` не зависит ни от чего;
- `Application` и `Infrastructure` зависят только от `Domain` и не знают друг о друге;
- `Api` зависит от `Application` и `Infrastructure` и связывает их между собой.

Обратных зависимостей нет. Технические детали можно заменить, не затрагивая модель предметной области.

## Прикладная логика

`Application` организован по CQRS. Операция — это пара «сообщение и обработчик»:

- команда меняет состояние;
- запрос читает состояние и не меняет его.

Сообщение доставляет обработчику медиатор. Контроллер отправляет сообщение и не знает, как операция реализована. Пары сообщение — обработчик связываются генератором кода на этапе компиляции, без рефлексии во время работы.

## Слой Api

`Api` — composition root. Здесь регистрируются зависимости всех слоёв и собирается конвейер обработки запросов.

Соглашения:

- HTTP-эндпоинты оформляются контроллерами, не Minimal API;
- контроллер не содержит логики: принимает запрос, отправляет сообщение медиатору, возвращает результат;
- маршрут контроллера включает версию API и имеет вид `api/v1/<контроллер>`;
- URL приводятся к нижнему регистру;
- описание API в формате OpenAPI генерируется из контроллеров и публикуется только в среде разработки;
- обработка исключений подключается из общего проекта — см. [Обработка исключений](exception-handling.md).

## Технологии

| Назначение | Технология |
| --- | --- |
| Целевая платформа | .NET 10 |
| Хост и HTTP-слой | ASP.NET Core |
| Медиатор CQRS | `Mediator` (martinothamar) |
| Описание API | OpenAPI (`Microsoft.AspNetCore.OpenApi`) |

Во всех проектах включены `Nullable` и `ImplicitUsings`.

## Доступ к данным

Обращение к базе данных — ответственность слоя `Infrastructure`.

Сейчас с базой данных не работает ни один сервис: ни контекста данных, ни зависимостей от СУБД в коде нет. В манифесте инструментов `PingService` закреплён `dotnet-ef` — CLI миграций Entity Framework Core.

## Общее между сервисами

Сервисы не переиспользуют код друг друга. Общий для них только сквозной код из `Backend/BuildingBlocks`: сейчас это обработка исключений.
