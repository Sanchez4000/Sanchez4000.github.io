# Архитектура

## Идея

Проект состоит из трёх видов частей:

- клиентское приложение;
- API-шлюз;
- несколько бэкенд-сервисов.

Шлюз — единая точка входа для внешних запросов. Он не содержит бизнес-логики и не проверяет авторизацию. Его задача — принять запрос и передать его нужному сервису, туда и обратно.

Бэкенд-сервисы содержат бизнес-логику, работают с базой данных и сами отвечают за проверку авторизации. Разные сервисы могут быть по-разному открыты: одни доступны без авторизации, другие требуют её. Это решает каждый сервис сам, а не шлюз.

Каждый сервис независим от других: своё решение, свои зависимости, свой цикл разработки. Все они собраны по единому архитектурному шаблону — см. [Бэкенд-сервис](backend-service.md).

Клиент обращается к системе через шлюз, а не напрямую к сервисам.

## Схема

```
Frontend (SPA)
      │
      ▼
   Gateway (тонкий прокси, без авторизации)
      │
      ├──▶ Backend-сервис 1 (открытый)
      ├──▶ Backend-сервис 2 (требует авторизации)
      └──▶ Backend-сервис N
```

## Состояние на сегодня

Части репозитория созданы независимо и пока не связаны друг с другом:

- у клиента нет обращений к API;
- у шлюза настроен только пример маршрута, без реального сервиса;
- бэкенд-сервисы ещё не созданы.

Это ожидаемое состояние для раннего этапа разработки, а не ошибка конфигурации.

## Решения и сборка

Каждый бэкенд-сервис собирается и открывается отдельно, как своё `.NET`-решение. Общего решения на весь репозиторий нет и не планируется — сервисы должны оставаться независимыми друг от друга.
