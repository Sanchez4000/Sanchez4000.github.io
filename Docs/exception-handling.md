# Обработка исключений

## Идея

Каждый бэкенд-сервис приводит необработанные исключения к одному формату ответа. Логика этого приведения одна и та же для всех сервисов, поэтому она не пишется в каждом сервисе заново, а переиспользуется.

Переиспользуемая часть оформляется отдельно от конкретного сервиса — как отдельный проект (библиотека), на который сервисы ссылаются. Сервис подключает её и регистрирует при старте, без копирования кода.

Это часть кросс-cutting слоя: то, что нужно каждому сервису одинаково, но не относится к его бизнес-логике.

## Механизм

Используется встроенный в ASP.NET Core механизм — `IExceptionHandler`. Он перехватывает необработанное исключение до того, как оно дойдёт до клиента как сырая ошибка сервера, и формирует ответ по единым правилам. Это заменяет `try/catch`, разбросанный по контроллерам.

## Формат ответа

Ответ — JSON-объект в формате ProblemDetails (RFC 7807), стандартном для ASP.NET Core. Клиент, сделавший запрос, получает читаемую структуру, а не голый текст исключения. Пример полей: код статуса, заголовок ошибки, описание.

Это открытый формат — клиент может разобрать его штатными средствами, без знания внутреннего устройства сервиса.

## На что обратить внимание при переносе в общую библиотеку

- Текст `Detail` не должен быть текстом исключения напрямую. Внутреннее сообщение исключения может содержать детали реализации (имена таблиц, путь к файлу, стек вызовов). Наружу должно уходить безопасное, заранее подготовленное сообщение, а полный текст — только в лог.
- Код статуса не обязан быть всегда 500. Разные типы исключений — например, "не найдено" или "нет доступа" — должны получать соответствующий код (404, 403 и т.д.), а не единый статус на все случаи.

## Состояние на сегодня

Общая библиотека ещё не выделена — конкретного бэкенд-сервиса, к которому её подключать, пока нет. Решение зафиксировано как план для следующего сервиса.
