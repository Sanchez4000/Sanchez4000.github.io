# Обработка исключений

Единый формат ответа об ошибке для всех бэкенд-сервисов. Реализация — в `Backend/BuildingBlocks`.

## Подключение

Сервис ссылается на проект `BuildingBlocks` и при старте регистрирует обработчик одним вызовом метода расширения. Код обработки в сервисах не дублируется.

## Механизм

Используется механизм ASP.NET Core `IExceptionHandler`. Обработчик перехватывает исключение до того, как оно дойдёт до клиента, и сам формирует ответ. Блоки `try/catch` в контроллерах для этого не нужны.

## Формат ответа

Тело ответа — JSON в формате ProblemDetails (RFC 7807), стандартном для ASP.NET Core.

| Поле | Содержимое |
| --- | --- |
| `status` | Код HTTP-статуса |
| `title` | Краткое название ошибки |
| `detail` | Описание ошибки |

Код статуса самого ответа совпадает со значением поля `status`. Формат открытый, поэтому клиент разбирает ошибку штатными средствами и не зависит от устройства сервиса.

## Классы исключений

Разным ошибкам соответствуют разные коды статуса. Их задаёт иерархия исключений с общим базовым классом `AppException`. Базовый класс объявляет контракт — код статуса и название. Наследник задаёт конкретные значения.

| Исключение | Статус | Название |
| --- | --- | --- |
| `ValidationException` | 400 | Некорректный запрос |
| `ForbiddenException` | 403 | Доступ запрещён |
| `NotFoundException` | 404 | Не найдено |

## Правило обработки

Обработчик различает два случая.

**Исключение наследует `AppException`.** Это ожидаемая ошибка, выброшенная прикладной логикой осознанно. Её статус, название и сообщение уходят клиенту как есть.

**Любое другое исключение.** Это сбой. Клиент получает статус 500 и обезличенный текст, подробности остаются в логе.

То же разделение действует в логах: ошибки со статусом 500 и выше пишутся на уровне `Error`, остальные — на уровне `Warning`.

## Новый вид ошибки

Новый вид ошибки — это новый класс-наследник `AppException` со своим кодом статуса и названием. Обработчик при этом не меняется.
